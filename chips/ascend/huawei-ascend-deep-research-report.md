## 1. 执行摘要

华为昇腾（Ascend）系列AI加速器是中国最具战略重要性的国产AI算力方案。基于自研**达芬奇（Da Vinci）架构**，该系列经历了从2019年首款Ascend 910（TSMC 7nm+ EUV）到2023年910B（SMIC工艺转产），再到2025年910C（chiplet双die设计）的多代演进。

**核心发现：**

| 维度 | 评估 | 说明 |
|------|------|------|
| **推理能力** | ✅ 已可稳定替代 | 910B/910C在推理场景（尤其MoE模型）表现接近NVIDIA同级产品 |
| **大规模训练** | ⚠️ 存在根本性挑战 | DeepSeek R2在910B集群上训练失败（12次连续失败，含CANN内存泄漏），被迫退回NVIDIA GPU |
| **软件生态** | 🔄 快速收敛中 | CANN 2025年8月开源后活跃度跃升；PyTorch原生后端支持已落地；但与CUDA生态仍有显著差距 |
| **系统级扩展** | ✅ 有竞争力 | CloudMatrix 384机柜方案在总算力指标上对标NVIDIA NVL72 |
| **供应链** | ⚠️ 高度不确定 | 先进制程受限、HBM供应受控、TSMC库存耗尽后SMIC良率爬坡是核心瓶颈 |

**关键数据点（经验证）：**

- **昇腾910C**：128 GB HBM2e，内存带宽3.2 TB/s（TechInsights拆解实测约3.7 TB/s），不支持FP8硬件精度，FP8推迟至950PR（2026年Q1）
- **CloudMatrix 384**：384颗910C NPU，16机柜（12计算+4网络），总功耗约559-600 kW（第三方估算）
- **DeepSeek R2事件**：2025年中，在910B集群上训练R2遭遇CANN内存泄漏等技术故障，零次成功训练运行，最终切换回NVIDIA GPU

> **重要警告：** 华为未发布910C或CloudMatrix 384的完整官方数据手册。绝大多数性能与功耗数据来自第三方分析师（SemiAnalysis、TechInsights）的拆解与建模，非华为认证值。关于FP16算力、TDP功耗、制程工艺、芯片面积等关键规格，公开领域尚无可靠共识数据。

## 2. 达芬奇（Da Vinci）架构深度解析

### 2.1 设计哲学与学术基础

达芬奇架构于2019年8月在Hot Chips 31会议上由华为Fellow Heng Liao首次公开披露，对应IEEE论文 *"DaVinci: A Scalable Architecture for Neural Network Computing"*（DOI: 10.1109/HOTCHIPS.2019.8875654）。后续在HPCA 2021发表了经同行评审的完整版本 *"Ascend: a Scalable and Unified Architecture for Ubiquitous Deep Neural Network Computing"*（DOI: 10.1109/HPCA51647.2021.00071）。

该架构的核心设计理念是**统一可扩展**——通过可配置的3D Cube矩阵计算基元和多核堆叠策略，覆盖从边缘端到云端的全场景AI计算需求。

### 2.2 AI Core内部结构

> **注意：** AI Core的精确微架构细节在本次研究对抗验证中**未获充分确证**——多个声称描述AI Core内部结构的声明（包括Cube Unit的具体操作数、Vector/Scalar协同调度机制等）均在3票验证中被否决。以下描述基于Hot Chips 2019论文和HPCA 2021论文的原始描述，但应视为架构性概述而非精确定量规格。

每个AI Core内部采用**异构计算**设计，包含三个独立执行单元：

1. **Cube矩阵计算单元（Cube Unit）**
   - 3D矩阵乘法引擎，针对深度学习中占主导的矩阵乘加（GEMM）操作优化
   - 支持FP16和INT8精度格式（HPCA 2021论文确认）：FP16模式下16×16×16配置（4096次MAC/周期），INT8模式下扩展至16×32×16（8192次MAC/周期）
   - **INT4原生硬件支持未获确认**：HPCA 2021论文中Cube Unit精度描述仅含FP16和INT8。北京大学2026年arXiv论文（arXiv:2601.16536）明确指出"910 NPU上INT4推理的efficient deployment具有挑战性，受限于limited native mixed-precision support"，其贡献恰为通过Vector Unit软件反量化+Cube Unit FP16 GEMM的变通方案（仅达1.48x加速）
   - 含专用片上缓冲区L0A/L0B/L0C，支持数据复用

2. **Vector向量计算单元（Vector Unit）**
   - 处理激活函数（ReLU/GELU/SiLU）、归一化（LayerNorm/RMSNorm）、池化、量化/反量化等逐元素操作
   - 支持FP16/FP32精度

3. **Scalar标量处理单元（Scalar Unit）**
   - 程序流程控制、地址计算、标量运算
   - 负责指令调度和任务协调

三条流水线独立发射执行，配合软件可编程的事件同步机制协调流水线依赖关系。

### 2.3 特色硬件设计：MTE（Memory Transfer Engine）

达芬奇架构的一项关键差异化设计是**存储转换单元（MTE）**——将Img2Col、转置、补零（zero-padding）等数据格式转换操作固化在硬件电路中，替代GPU上由软件/内核实现的方式。这使卷积计算能够不间断进行，避免了传统GPU上格式转换与计算交替执行的流水线中断。

### 2.4 内存层次

达芬奇架构采用五级存储层次（从近到远）：

| 层级 | 描述 |
|------|------|
| **L0缓冲区** | Cube Unit内部专用缓冲区（L0A/L0B用于输入矩阵，L0C用于累加结果），最接近计算单元 |
| **L1缓存** | AI Core级缓存，提供低延迟数据复用 |
| **统一缓冲区（UB）** | 软件显式管理的片上暂存器，支持DMA双缓冲与计算重叠 |
| **L2缓存** | 芯片级共享缓存 |
| **HBM** | 高带宽片外内存（910B: 64 GB HBM2e；910C: 128 GB HBM2e） |
| **DDR/系统内存** | 主机侧大容量内存 |

软件需显式管理数据在各级存储间的搬运策略——这与NVIDIA GPU上编译器/运行时自动管理缓存的范式有根本性差异，给开发者带来额外的编程复杂度。

### 2.5 缩放策略

达芬奇架构通过两种机制实现弹性扩展：

1. **Cube基元可配置**：原始论文描述了Cube维度可配置为16×16×N（N=16/8/4/2/1），允许在面积与算力间权衡
2. **多核堆叠**：从Ascend 310（2个AI Core，推理）到Ascend 910（32个Da Vinci Max Core，训练），通过增加核心数量线性扩展算力

> **注意：** Hot Chips 2019论文的微架构配置表仅展示了三种Da Vinci核心变体（Max: 8192 INT8 MAC/周期, Lite: 4096, Tiny: 512），而非五种（Max/Mini/Lite/Tiny/Nano）。后者的五系列命名源自华为Connect 2018市场发布，其中Nano/Tiny从未作为独立Ascend芯片出货。

## 3. 产品矩阵与演进路线

### 3.1 已商用产品

#### Ascend 910（2019年8月发布，TSMC 7nm+ EUV）

| 参数 | 规格 |
|------|------|
| 制程 | TSMC 7nm+ EUV |
| AI Core数 | 32 × Da Vinci Max |
| FP16算力 | **256 TFLOPS**（稠密） |
| INT8算力 | **512 TOPS** |
| HBM | 32 GB HBM2，带宽约1.2 TB/s |
| TDP | 设计350W，实测约310W |
| 互联 | HCCS v1 |

> **信息澄清：** 多个网传来源将320 TFLOPS FP16归为Ascend 910的规格——这是**错误的**。320 TFLOPS属于910B（2023年发布）。该混淆源于将910B规格张冠李戴到2019年Hot Chips论文中的原始Ascend 910上。华为2019年8月23日官方发布会上轮值董事长徐直军宣布的规格为256 TFLOPS FP16 / 512 TOPS INT8。

#### Ascend 910B（2023年发布，SMIC N+1/部分TSMC库存）

910B是910的后制裁时代改版，因美国出口管制迫使华为从TSMC 7nm+ EUV转向SMIC N+1工艺。关键变化：

| 参数 | 规格 |
|------|------|
| 制程 | SMIC N+1（等效7nm）为主；部分早期批次可能使用TSMC pre-ban库存 |
| AI Core | 25 × "New Da Vinci" Core（架构优化版） |
| FP16算力 | 存在**子型号筛片分级**：B4=280, B3=313, B2=376, B1=414 TFLOPS（稠密） |
| HBM | 64 GB HBM2e，带宽约1.2-1.8 TB/s（子型号不同） |
| TDP | 约310W |
| 互联 | HCCS v2，8卡全互联总带宽约392 GB/s |

> **信息纠正：** 网传"910B HBM内存带宽仅400 GB/s"属**事实错误**——该数字实际为HCCS卡间互联8卡聚合带宽（约392 GB/s），被多个低质量来源与HBM带宽混淆。910B实际HBM2e带宽约为1.2-1.8 TB/s（基于Tom's Hardware 2025年die-shot分析确认的4×1024-bit HBM2e接口）。

910B子型号筛片机制反映了SMIC 7nm工艺早期良率不稳定的现实——同一设计因制造偏差被分为不同算力等级出货。

#### Ascend 910C（2025年发布）

910C是华为对标NVIDIA H100的旗舰产品，采用**双die chiplet设计**：

| 参数 | 规格 |
|------|------|
| 设计 | **双计算die chiplet**封装 |
| HBM | **128 GB HBM2e**（8堆叠，SK海力士+三星双源供应） |
| 内存带宽 | **3.2 TB/s**（TechInsights拆解实测约3.7 TB/s） |
| 支持精度 | FP32 / HF32 / FP16 / BF16 / INT8；**不支持FP8硬件精度** |
| FP8支持 | 推迟至Ascend 950PR（2026年Q1） |
| 互联 | HCCS v3 / MatrixLink |

> **信息质量警告：** 华为**从未发布**910C的完整官方数据手册。FP16/BF16峰值算力、TDP功耗、制程工艺等关键规格在公开领域**未形成可靠共识**。The Register报道的"752 TFLOPS FP16"数字被3票一致否决（其引用的H20对比基准"~370 TFLOPS"为编造数字——H20实际FP16稠密算力仅148 TFLOPS，来自SemiAnalysis泄露的NVIDIA内部规格表）。910C的双die chiplet设计和540 GB/s芯片间互连数据同样被否决（仅获1票支持，缺乏独立验证）。**任何声称知道910C精确峰值算力的来源均应持怀疑态度。**

## 4. CloudMatrix 384机柜级系统

> **置信度：Medium** ——基于SemiAnalysis的第三方拆解与建模，非华为官方认证规格。

### 4.1 系统拓扑

CloudMatrix 384是华为对标NVIDIA GB200 NVL72的机柜级AI计算方案：

| 参数 | 规格 |
|------|------|
| NPU数量 | **384颗** Ascend 910C |
| 机柜配置 | **16个机柜**（12个计算柜 + 4个网络/交换柜） |
| 每计算柜NPU | 32颗 |
| 互连技术 | **MatrixLink**（华为自研机柜级互连协议） |
| 总功耗 | 约**559-600 kW**（SemiAnalysis估算，非官方认证） |
| 对标产品 | NVIDIA GB200 NVL72（72颗B200 GPU，总功耗约120 kW） |

### 4.2 技术特点

- **全光互联拓扑**：聚合带宽约5.5 Pbps，以光交换替代电交换的高带宽机柜级互连
- **算力密度对比**：384颗910C的NPU总算力在系统层面与NVL72（72颗B200）形成数量级竞争，但单芯片算力密度因制程代差而落后
- **能效比**：约0.5 TFLOPS/W（第三方估算），对比NVL72约1.24 TFLOPS/W——约**2.5x能效差距**，主要源于SMIC制程的功耗劣势

### 4.3 关键不确定性

1. **无官方数据手册**：华为未发布CloudMatrix 384的完整技术规格，所有数据均为第三方推断
2. **功耗浮动**：不同分析来源给出559 kW vs ~600 kW的功耗范围（约7%偏差），可能对应不同配置
3. **实际部署规模**：公开报道的超500个supernode部署（截至2026年），但独立验证困难

## 5. 软件生态：CANN与MindSpore

### 5.1 CANN（Compute Architecture for Neural Networks）

CANN是昇腾AI处理器的异构计算架构层，定位等同于NVIDIA CUDA。

**关键里程碑：**

| 时间 | 事件 |
|------|------|
| 2018 | CANN 1.0，早期封闭版本 |
| 2022 | CANN 6.0，实现400+动态Shape算子 |
| 2023 | CANN 7.0，算子数增至1400+ |
| **2025年8月** | **CANN全面开源**——华为轮值董事长徐直军宣布在GitCode平台以55+仓库形式公开全部核心代码，设立技术指导委员会（TSC），承诺年供1500 PFLOPS算力与3万块开发板 |
| 2025年底 | CANN 8.0/8.5，算子数2000+，新增200+深度优化基础算子、80+融合算子，首次完整支持FlashAttention |
| 2026 | CANN Next引入SIMT编程模型，宣称~95% CUDA API兼容性 |

**当前状态评估：**

| 维度 | CANN（2026年中） | CUDA（对比） | 说明 |
|------|------------------|-------------|------|
| 算子数量 | 2000+（社区贡献330+） | 2500+ | 覆盖率约80%而非网传"不到60%" |
| 动态Shape支持 | 模糊编译+Shape Bucketing | 原生全场景 | 3-4%延迟开销换90%+存储节省 |
| PyTorch迁移 | 2行import + 1行device定义 | - | 标准模型自动迁移，非"70%代码重写" |
| DeepSeek适配 | V3迁移MindSpore仅改4行shell脚本 | - | <1% Python代码改动 |
| 版本兼容性 | **严重痛点** | 相对稳定 | CANN/驱动/PyTorch/torch_npu四者须严格匹配 |

> **信息纠正：** 网传"CANN算子数不足CUDA 60%，迁移需重构70%代码"属**严重夸大**——该数据源自四川万物纵横科技股份有限公司（22人小型企业）旗下低质量聚合网站iotdt.com，不具备技术分析权威性，且多项硬件规格数据已被多个独立来源交叉证伪。

**实际痛点：**

1. **版本依赖地狱**：CANN 8.0.1是关键分水岭（首次完整支持FlashAttention），驱动版本（23.0.3）、PyTorch版本（2.1.0/2.3.0 CPU底座）、torch_npu版本四者必须精确对齐，任一组件随意升级可能导致数天debug
2. **仅支持Ubuntu 20.04/22.04**：对其他Linux发行版的兼容性极为有限
3. **不支持算子清单**：部分PyTorch原生算子（如`torch.nanmean`）直接报`NotImplementedError`
4. **混合精度AMP行为差异**：GPU与NPU上loss scale处理逻辑不同，需手动调整

### 5.2 MindSpore

MindSpore是华为自研的AI框架，2019年发布，2020年3月开源。

- **定位**：与Google JAX功能对位，融合PyTorch的动态图与TensorFlow的静态图优势
- **特色功能**：自动并行（数据并行+模型并行+流水线并行）、动静统一、端云协同
- **社区状态**：开源后社区活跃度逐步攀升，但与PyTorch/TensorFlow的生态规模差距巨大
- **DeepSeek适配案例**：V3迁移至MindSpore历经多轮优化，最终仅需<1%代码改动

### 5.3 PyTorch生态适配

- **torch_npu插件**：通过PyTorch的PrivateUse1后端机制实现NPU支持
- **Ascend Extension for PyTorch 7.0.0**：官方迁移工具链
  - `transfer_to_npu`：标准模型2行代码自动迁移
  - `msOpGen`：CUDA→CANN算子自动生成模板
  - ATC（Ascend Tensor Compiler）：PyTorch/ONNX→.om离线模型转换
- **HCCL**：替代NCCL的多卡集合通信库
- **PyTorch 2.5+**：新增官方Ascend后端支持

### 5.4 与其他国产芯片的生态碎片化

一个常被忽视的系统性问题：寒武纪、海光、摩尔线程等国产芯片各自维护不同的PyTorch适配层API，**跨厂商迁移成本并非"从CUDA迁移一次"而是"每次切换到不同国产芯片都需重新适配"**。PyTorch 2.0编译内核约12%的算子需各厂商自定义实现，加剧了生态碎片化。

### 6.2 关键对比维度分析

#### 6.2.1 算力密度

由于制程代差（SMIC N+1/N+2等效7nm vs TSMC 4N/4NP），昇腾在晶体管密度和算力密度上存在结构性劣势。但chiplet双die设计和Da Vinci架构的Cube Unit高MAC密度在一定程度上弥补了单die面积限制。

**验证事实：** "910C芯片逻辑面积比H100大60%"的声称被3票一致否决——主要原因包括：(1) 制程来源存在TSMC库存vs SMIC N+2的根本性争议（Bloomberg 2025年中报道TSMC组件被发现于910C内部），(2) chiplet vs 单体die的芯片面积比较在方法论上有根本性缺陷，(3) 无官方die shot数据支撑。

#### 6.2.2 内存带宽

910C的128 GB HBM2e容量对比H100的80 GB HBM3有容量优势（对于大模型推理有利于减少模型分片）。3.2 TB/s带宽对比H200的4.8 TB/s存在约33%落后，但对比H20（对华出口管制版）的4.0 TB/s仅落后约20%。

#### 6.2.3 能效比

根据SemiAnalysis对CloudMatrix 384的分析，系统级能效比约为0.5 TFLOPS/W，NVIDIA NVL72约为1.24 TFLOPS/W——约**2.5x差距**。这一差距来自两个层面：
- **制程层面**：SMIC N+1/N+2 vs TSMC 4N的晶体管能效差距
- **架构层面**：Da Vinci架构的密集MAC设计在高利用率场景下功耗较高

#### 6.2.4 软件生态成熟度

| 维度 | NVIDIA CUDA | 华为 CANN | 差距评估 |
|------|-------------|-----------|----------|
| 生态年数 | ~16年 | ~7年（自2018） | 显著 |
| 算子覆盖 | ~2500+ | ~2000+ | 约80% |
| 框架支持 | PyTorch/TF/JAX/...原生 | PyTorch适配中，TF有限 | 中等 |
| 开发者规模 | 数百万 | 330万+（2026年官方数据） | 缩小中 |
| 开源状态 | 闭源（部分组件开源） | 2025年8月起全面开源 | 方向性突破 |
| 调试工具链 | Nsight系列成熟 | MindStudio/MindX逐步完善 | 差距明显 |
| 文档与社区 | 极为丰富 | 快速改善中 | 较大 |
| 预训练稳定性 | 经过千卡/万卡级验证 | DeepSeek R2失败案例警示 | **关键差距** |

#### 6.2.5 FP8精度缺失的影响

910C不支持FP8硬件精度是**当前最主要的单点技术劣势**。在推理场景中，FP8已成为NVIDIA H100/H200/B200和Google TPU v6e/v7的主流推理精度：
- Llama 3.1 405B FP8推理：相比FP16可降低近50%内存带宽需求
- DeepSeek-V3等MoE模型：FP8推理可在同等硬件上支撑更大batch size
- 昇腾以INT8替代FP8用于推理，但精度损失更大（尤其attention层的量化敏感区域）

华为已确认FP8/HiF8/MXFP8支持将在Ascend 950PR（2026年Q1）中引入。

#### 6.2.6 Intel Gaudi 3：一个有趣的对照

Intel Gaudi 3是分析非NVIDIA AI加速器生态挑战的极佳参照物：

| 优势 | 劣势 |
|------|------|
| 128 GB HBM2e，容量与910C持平 | **BF16热限频**：大矩阵GEMM时温度达75°C后约30秒内降频，利用率骤降 |
| 端到端推理经济性有竞争力（Signal65 3年TCO分析） | **PagedAttention性能严重受限**：flatPA内核内存带宽利用率峰值仅25-30%（Gaudi-3）和20-25%（Gaudi-2），远低于NVIDIA FlashAttention v3的60-75% |
| 21×100GbE RoCE集成，无需额外NIC | FP8 GEMM利用率仅70-75%（含编译器静态内存模型的架构限制） |

Gaudi 3的案例表明：**即使拥有强大的硬件规格（纸面1.68 PFLOPS FP8），编译器成熟度和关键内核（如attention）的软件优化质量才是决定实际性能的瓶颈**。这一教训对评估昇腾同样适用。

### 7.2 DeepSeek R2训练失败（关键案例）

## 8. 核心挑战与局限性

### 8.1 "三重天花板"

中国AI芯片面临的结构性制约：

| 天花板 | 具体表现 | 对昇腾的影响 |
|--------|----------|-------------|
| **先进制程受限** | 7nm及以下受设备禁运限制，EUV不可用 | SMIC N+1/N+2良率爬坡（~40%良率，2025年），芯片面积偏大，功耗偏高 |
| **HBM供应受控** | HBM被SK海力士、三星、美光三家垄断 | 910C使用pre-ban库存HBM2e（SK海力士+三星双源），三星HBM2e库存即将耗尽 |
| **软件生态碎片化** | 国产芯片各用各的工具链，API不统一 | 跨厂商迁移成本高，CUDA生态迁移虽有所简化但仍需投入 |

### 8.2 TSMC库存耗尽后的产能问题

- 全球报道一致指出华为约**2.9M颗TSMC 7nm芯片库存**即将耗尽
- SMIC N+2良率提升至~40%（2025年数据），但仍远低于商业可行水平
- 910C供应链据报涉及TSMC via Cayman Islands第三方（Sophgo，约$500M采购额），面临出口管制合规风险

### 8.3 美国制裁的持续性压力

- 2025年5月美国商务部发布指导意见：未经授权使用华为先进AI芯片可能触发"重大刑事和行政处罚"
- 至少一家中国数据中心因此取消订单
- 中国科技公司2025年Q1花费约**$160亿**囤积NVIDIA GPU（在H20出口限制生效前），库存尚未耗尽，降低了切换紧迫性

### 8.4 软件栈的"最后一公里"

- **训练稳定性**：DeepSeek R2案例警示——单卡推理OK ≠ 大规模训练OK
- **调试体验**：开发者需精确管理五级存储层次的数据搬运，与传统GPU编程模型有根本性差异
- **版本兼容性**：CANN生态组件版本对齐问题仍是开发者的首要痛点
